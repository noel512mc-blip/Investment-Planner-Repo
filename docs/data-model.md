# Milestone Data Model Proposal

## Purpose and scope

This document describes the browser-only prototype as it exists today, then proposes a small versioned model for investment-goal projections and household collaboration. It is a design proposal only. The website, its storage, and its calculations are unchanged.

The prototype stores hypothetical inputs and preferences. It does not store real investment accounts, securities, broker connections, or actual account balances.

## Current prototype

### Plan lifecycle

1. `createNewPlan()` creates an object with a generated ID such as `acct_<timestamp>`, a name, an empty `people` array, and default `settings`. It makes the plan active and calls `loadPlan()`.
2. `saveCurrentToPlan()` reads the visible person forms and settings from the DOM, builds the plan's `people` and `settings` fields, then calls `savePlansToStorage()`. Changes are also saved through existing app event paths. Plan names, deletion, duplication, and active-plan changes use the same save wrapper.
3. `readPlansFromStorage()` reads the plan collection and active ID. `loadPlansFromStorage()` assigns them to application state, renders the plan bar and list, then calls `loadPlan()` for the active plan if it exists. `loadPlan()` rebuilds people and settings in the form, selects the plan, and saves the selected ID.
4. `sharePlan()` first saves the current form, serializes one plan as JSON, Base64-encodes its UTF-8 bytes, and puts that data in a `?plan=` URL parameter. The URL carries a copy of plan data, not a live plan reference: it is not an account invitation or a private collaboration feature. Anyone with the URL can import a separate copy into their browser.

At startup, `loadPlansFromStorage()` restores saved plans and loads the saved active plan before the `?plan=` importer runs. A valid link is validated and normalized, assigned a new `shared_<timestamp>` ID, named with the ` (imported)` suffix, saved as the active plan, and loaded. After processing a non-empty `plan` parameter, the importer removes the query from the current URL, so reloading that URL does not import another copy.

Automatic startup imports and manual `importSharedPlan()` imports both call `decodeAndValidateSharedPlan()`, which decodes the payload and calls `validateAndNormalizeSharedPlan()`. The payload is limited to 350,000 Base64 characters and 256 KiB after decoding. The plan must have a `people` array (at most 10 entries) and a `settings` object; imported IDs, strings, booleans, numeric values, currencies, and household-member references are type- and range-checked. Person and plan names are limited to 256 characters, income labels to 128, and each person can have at most five additional income sources. Missing optional values receive defaults during normalization.

Manual import reports a missing parameter or invalid/oversized link with an alert; it also alerts if the browser already has 10 plans. Invalid manual imports do not change saved plans. Startup import silently ignores invalid links and links that exceed the 10-plan limit; when a non-empty parameter was processed, it is removed either way. Base64 is an encoding, not encryption, so the URL itself contains the plan data.

### Where current data lives

`localStorage` key `investment_plans` contains a JSON object map: each object key is a plan ID and each value is a plan. The plan ID is not repeated inside the plan object. Key `investment_activePlanId` stores the selected plan ID separately. The old keys `investment_accounts` and `investment_activeAccountId` are migrated when the corresponding new key is absent; the old key is then removed. Invalid JSON for `investment_plans` is caught and treated as an empty plan map.

There is no current schema version. Plan IDs use timestamp-based strings (`acct_...` or `shared_...`); person IDs are numeric IDs generated by the app and are not globally stable IDs.

### Current saved fields

| Current entity / field | Meaning and type | Units or notes | Current storage |
|---|---|---|---|
| Plan map key / plan ID | String key for one plan | Usually `acct_<timestamp>` or `shared_<timestamp>`; not inside the plan object | Key in `investment_plans` JSON object |
| `name` | Plan name; string | Shared-link imports append ` (imported)` | `investment_plans[planId].name` |
| `people` | Array of projected people | Empty when first created; form saves populate it | `investment_plans[planId].people` |
| `people[].id` | Numeric person ID | App-generated; used to connect form/results and `settings.householdMembers` | Each saved person object |
| `people[].name` | Display name; string | No account or login identity implied; imported names are limited to 256 characters and rendered as text | Each saved person object |
| `people[].initial` | Initial investment; number | Plan currency units; deposited at the person's start offset | Each saved person object |
| `people[].monthly` | Monthly contribution; number | Plan currency units per month | Each saved person object |
| `people[].increaseRate` | Annual contribution increase; number | Percent, e.g. `2` means 2%, not `0.02` | Each saved person object |
| `people[].startOffset` | Contribution start; number | Projection year offset; normally 1 or later | Each saved person object |
| `people[].stopOffset` | Contribution stop; number | Year offset; 0 means no stop; the stop year is exclusive | Each saved person object |

| `people[].retirementSettings.currentAge` | Current age; number | Years | Nested in each person's `retirementSettings` |
| `people[].retirementSettings.withdrawalGoal` | Retirement income target; number | Plan currency per month | Nested in each person's `retirementSettings` |
| `people[].retirementSettings.withdrawalRate` | Withdrawal rate; number | Percent | Nested in each person's `retirementSettings` |
| `people[].retirementSettings.statePensionEnabled` | Whether state pension is assumed; boolean | Per person | Nested in each person's `retirementSettings` |
| `people[].retirementSettings.statePensionAge` | State pension age; number | Years of age | Nested in each person's `retirementSettings` |
| `people[].retirementSettings.statePensionIncome` | State pension income; number | Plan currency per month | Nested in each person's `retirementSettings` |
| `people[].retirementSettings.additionalIncomeSources` | Array of income assumptions | Each item has `label` (string; imported labels limited to 128 characters), `amount` (number, plan currency per month), and `startAge` (number, age in years); up to five per person | Nested in each person's `retirementSettings` |
| `settings.years` | Projection horizon; number | Years | `investment_plans[planId].settings` |
| `settings.increaseRate` | Plan-level contribution increase field; number | Stored as 2 percent, but the current projection reads each person's `increaseRate` instead | `settings` |
| `settings.returnRate` | Shared annual return assumption; number | Percent | `settings` |
| `settings.perPersonReturn` | Whether each person has their own return; boolean | If false, `settings.returnRate` is used | `settings` |
| `settings.useInflation` | Whether values are adjusted for inflation; boolean | Affects displayed projections | `settings` |
| `settings.inflationRate` | Annual inflation assumption; number | Percent | `settings` |
| `settings.scenarioRange` | Scenario return range; number | Percentage points around the annual return, e.g. 2 means +/- 2 points | `settings` |
| `settings.currentAge`, `retirementAge` | Retirement defaults / legacy fallback values; numbers | Ages in years; person-specific settings take precedence on current saves | `settings` |
| `settings.noStatePension` | Inverse of the pension-enabled control; boolean | Legacy/default retirement fallback | `settings` |
| `settings.withdrawalGoal`, `withdrawalRate`, `statePensionIncome` | Retirement defaults / legacy fallback values; numbers | Monthly currency target/income and withdrawal percent | `settings` |
| `settings.householdMembers` | Array of numeric person IDs included in the household projection total | This is a selection of projected people, not household users or membership records | `settings` |
| `settings.currency` | Currency symbol; string | Current options are `€`, `$`, `£`, `¥`, and `₣`; used for display, not currency conversion | `settings` |
| `settings.startYear` | Display starting year; number | Calendar-year label anchor; does not change the investment simulation | `settings` |
| Active plan ID | String or absent | Which plan is selected in this browser | `investment_activePlanId`, separate from the plan JSON |

The retirement fields `currentAge`, `withdrawalGoal`, and related fields are saved both as per-person assumptions and as plan-level defaults/fallbacks. New saves include per-person retirement settings; `loadPlan()` retains fallbacks for older plan shapes.

### Inputs, derived results, and temporary state

The saved plan contains user-entered projection inputs and retirement assumptions. The calculation function returns `finalBalance`, `totalInvested`, `totalProfit`, year-end `balances`, and year-end `balancesInvested`; the application also calculates combined totals and base/bull/bear results. Those values feed the chart, summaries, and analysis UI. They are recalculated from inputs and are not fields in the saved plan JSON or shared-plan payload.

`householdMembers` is persisted as a list of included person IDs, but household totals are derived outputs. Other temporary interface state includes the highlighted person, selected analysis tab, chart instances, validation messages, open/collapsed panels, and retirement-analysis editing/locking state. These are not saved as plan fields.

The prototype does not model an actual holding, bank/broker account, or real balance. An initial amount and monthly contribution are assumptions for a hypothetical projection, not records of money already owned or invested.

## Proposed first product model

### Entities and relationships

Use stable, opaque IDs (for example UUIDs) rather than timestamps or list positions. A display name is not an ID. Store an explicit `schemaVersion` on every plan. The model below is intentionally limited to planning and household collaboration.

| Entity | Proposed purpose and relationships |
|---|---|
| `User` | A signed-in person. Has a stable `userId` and account/profile fields. Authentication secrets belong to an identity provider or secure auth system, not a plan JSON document. |
| `Household` | A shared planning space. Has a stable `householdId`; contains memberships and can own plans. It is not itself a person's investment balance. |
| `HouseholdMembership` | Joins one `User` to one `Household` using `userId` and `householdId`. A role/status can be represented, but its permissions and whether it links to a `Person` remain product decisions. |
| `Plan` | A versioned projection workspace. Belongs either to one user or one household; records its creator, currency, people, assumptions, goals, and scenarios. |
| `Person` | A named planning subject whose inputs are projected. A Person is not automatically a login User and has no actual investments by implication. Belongs to a plan in this small proposal. |
| `Goal` | A measurable desired outcome, linked to a plan and optionally a Person; a household-wide goal can have no `personId`. Holds a target and a date or age rather than calculated results. |
| `Scenario` | A named alternative projection, linked to a plan. Holds explicit assumption overrides (for example a lower annual return); its balance series is calculated, not stored as the scenario definition. |
| `Assumptions` | Versioned inputs used by a plan or person. Plan assumptions provide defaults; optional person assumptions override them. Contains contribution, return, inflation, horizon, and retirement inputs, not actual holdings. |

A household-owned plan should be identifiable through `householdId`; a personal plan through `ownerUserId`. Treat these as mutually exclusive ownership choices. `createdByUserId` records who created it but does not by itself grant access. The exact rule for who can edit the shared plan is unresolved; do not rely on frontend checks as authorization. The backend must enforce whatever policy is chosen.

`Person` remains separate from `User`: a planning profile can exist before a collaborator has an account, and a user can exist without being a projected investor. Whether a membership should link to one Person is an open decision. Likewise, distinguish a household's people in a projection from its signed-in members.

A household membership would be a separate record joining a `userId` and `householdId`; it is deliberately not inferred from the `Person` record. The example's goal describes a target, while the projected portfolio value remains calculated output.

### Keep projections separate from actual money

`Person` and `Assumptions` describe what-if inputs. Projection results describe what the model estimates from those inputs. Neither means money is currently held.

If actual financial data is added later, give it separate account/holding entities, separate permissions, and a separate source/verification status. Do not write actual balances into `initialAmount`, do not label a projected `finalBalance` as an account balance, and do not silently combine actual and hypothetical values in one total. Actual accounts and broker imports are outside this model's scope.

For ownership, a personal plan belongs to a User; a shared plan belongs to a Household. A Person's personal retirement assumptions may be sensitive even within a household. Whether those fields are visible/editable to all household members is unresolved and must be decided before collaboration ships.

## Frontend and backend agreement

Settle these questions together before implementing real accounts or shared households:

- Is a plan personal, household-owned, or either? Can it be moved, copied, or shared between those scopes?
- What does each household role mean? Who can view, edit, invite, delete, export, or change ownership? Are any Person assumptions private?
- Is each HouseholdMembership linked to a Person? Can a household contain planning people without accounts, and can one User map to multiple people?
- Which fields are canonical, which have plan defaults and person overrides, and how are old plan versions upgraded? Which side is authoritative for calculations?
- What are the units and rounding rules for money, percentages, inflation, dates, and year offsets? Is currency just display or does conversion ever occur?
- Are goals personal or household-wide, and can one goal apply to multiple people? Which goal types are in the first release?
- Are scenarios saved as named overrides, or generated from one range setting as today? Should calculated results ever be cached, and how are calculation versions identified?
- How does the UI handle simultaneous edits, conflict detection, undo, deletion, and restore? Is active-plan selection per user, browser, or device?
- Are share links public bearer links? Do they expire, expose personal assumptions, or support revocation? What should importing a link do to ownership?
- What are the export, retention, account deletion, household departure, and audit-history expectations?

Suggested role labels such as `owner`, `editor`, and `viewer` are only vocabulary candidates. Their permissions are not defined by this proposal.

## Staged migration from the prototype

1. **Freeze and document the prototype shape.** The current browser data is a plan map with a separate active-plan key, no embedded stable plan ID, and no schema version. Keep a test export while the new contract is finalized.
2. **Define version 1 and converters.** Choose stable IDs and an explicit `schemaVersion`. Map current plan map keys to `Plan.id`; convert numeric person IDs to stable Person IDs and update references such as household inclusion; move current settings and person fields into clearly named assumptions. Preserve percentage units, currency labels, and zero/null meanings deliberately. Do not copy calculated balances into the new input records.
3. **Choose a prototype cutover.** Because these browser plans are test data, a clean reset is acceptable. If chosen, explain that plans in that browser will disappear and clear only the app's named keys after explicit confirmation. Do not reset browser storage as a side effect of loading a new app version.
4. **If real user data exists by then, migrate opt-in.** Offer an export/backup, show a preview of each converted plan and its owner, ask the user to confirm personal versus household ownership, and import idempotently. Keep the original local data available until the server copy is verified; report invalid or unsupported fields instead of silently dropping them.
5. **Roll out collaboration separately.** After single-user versioned plans are stable, add server authorization and memberships. Do not infer household members or permissions from the prototype's `settings.householdMembers` list; it only lists selected projection people.

This proposal does not authorize a reset or migration now. No running code or browser storage was changed while preparing it.
